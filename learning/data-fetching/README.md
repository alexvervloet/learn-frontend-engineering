# Data fetching 🟢

TanStack Query, and the reasons it exists. Seven lessons on caching,
mutations, optimistic updates and paging, then the smaller library that does
most of it and the three ways a server pushes instead of answering. All against
a mock network that runs in the browser and in the tests without changing.

No backend needed. MSW intercepts the requests.

## What the files cover

| File                        | What it teaches                                                                                                               |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |

| `02_keys_and_staleness.tsx` | The key _is_ the cache. `staleTime` is how long you trust an answer; `gcTime` is how long you keep it after nobody is looking |
| `03_mutations.tsx`          | `useMutation`, prefix-matched `invalidateQueries`, and showing the message the API actually sent                              |
| `04_optimistic.tsx`         | Cancel, snapshot, guess, roll back. Why `cancelQueries` is the step you cannot skip                                           |
| `05_infinite.tsx`           | `useInfiniteQuery`, cursors over offsets, and letting the server decide where the list ends                                   |
| `06_swr.tsx`                | The same cache and dedup in a third of the bundle, and the four things you write yourself instead                             |
| `07_realtime.tsx`           | Polling, SSE and WebSockets. The SSE wire format, backoff with jitter, and why the cache is the state                         |

## Run it

```bash
npm install                          # from the repo root, once
npm run dev -w learning/data-fetching
npm test -- --project data-fetching
```

Open the React Query devtools in the corner. Every cache entry, its key, whether
it is stale, and who is subscribed to it, which turns "why did that refetch"
into something you read rather than guess.

## Why MSW rather than mocking fetch

Stubbing `global.fetch` or mocking the module that calls it tests a version of
your code with a seam cut into it. MSW intercepts at the network layer, so the
component makes a real request through the real client, and the only thing
swapped out is the server. The same handlers then run the browser demo, which
means the mock and the thing you clicked through cannot drift apart.

`onUnhandledRequest` differs between the two on purpose. Tests use `"error"`, so
a typo in a URL fails with "no handler for GET /api/bookmark" instead of hanging.
The browser uses `"bypass"`, because the worker also sees Vite's own asset
requests.

## Three things that bit while writing the tests

**Counting requests is the only honest cache test.** Both panels in lesson 01
end up showing the right rows. `server.events.on("request:start", …)` is what
shows one of them asked three times and the other twice.

**A cache hit does not mean no request.** With the default `staleTime: 0`, a
revisit renders from cache _and_ refetches behind it. That is usually what you
want and it made the first version of lesson 01's assertion wrong.

**An in-flight request outlives the test that started it.** A vote asserted
optimistically, with the test ending before the 300ms request landed, wrote to
the fake database _after_ `afterEach` had reset it, and the next test started one
vote ahead. Wait for the write to land, not just for the screen to update.

## SWR and Query, side by side

Lesson 06 runs both against the same handler and counts the requests, so the
deduplication claim is a number rather than a paragraph. The summary:

**The same.** A cache keyed by the key, dedup, revalidate on focus and
reconnect, stale data on screen during a refetch. Expect all of these from
anything in this category.

**What SWR leaves out.** Mutations with an `onMutate`/`onError`/`onSettled`
lifecycle, so the rollback in lesson 04 becomes something you write. Prefix
invalidation, because keys are strings rather than arrays, so "everything under
bookmarks" is a predicate with your bug in it instead of the library's. And
devtools, which is the one you feel first.

**What it gains.** About a third of the bundle, no provider at the root, and
`useSWRSubscription`.

If the app mostly reads, SWR is less machinery for the same result. Once
mutations have to invalidate related things, the pieces you write by hand add
up to a worse version of what Query ships, which is why this module teaches
Query first.

## Real time, and what the tests can reach

jsdom has `WebSocket` and no `EventSource`, which decides the split in lesson 07.

The socket half runs against **MSW's `ws` link**, so the component opens a real
`WebSocket` to a real URL and a handler answers it. No injected fake socket and
no interface that exists only under test, which is the same argument this
module already makes for MSW over stubbing `fetch`.

The SSE half is tested at the parser, which is where the bugs are anyway:
a keep-alive comment that must not become an empty event, repeated `data:`
lines that join with a newline rather than replacing each other, the single
optional space after the colon, and a chunk boundary landing mid-event.

Two things worth taking away.

**The message is not the state.** A socket update goes into the query cache,
not into a list in the component. A reconnect then refetches and repairs
whatever was missed; an append-only array in `useState` keeps the gap and
nothing tells you.

**A message can beat the first query.** The socket opens well before a 300ms
fetch resolves, and patching a cache entry that does not exist yet writes
nothing at all, after which the in-flight response lands and the message is
gone. The component invalidates instead when there is nothing to patch, and a
test covers exactly that ordering.

## Not covered here

cache to storage, `useSWRInfinite`, presence and CRDTs on top of a socket, and
the server-side story where the data is fetched before the JavaScript ships. The
last of those belongs in next-app-router.
