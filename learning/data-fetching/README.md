# Data fetching 🟢

TanStack Query, and the reasons it exists. Five lessons on caching, mutations,
optimistic updates and paging, against a mock network that runs in the browser
and in the tests without changing.

No backend needed. MSW intercepts the requests.

## What the files cover

| File                        | What it teaches                                                                                                               |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `01_fetch_in_an_effect.tsx` | A careful hand-rolled fetch next to `useQuery`, counting requests. The difference is a cache                                  |
| `02_keys_and_staleness.tsx` | The key _is_ the cache. `staleTime` is how long you trust an answer; `gcTime` is how long you keep it after nobody is looking |
| `03_mutations.tsx`          | `useMutation`, prefix-matched `invalidateQueries`, and showing the message the API actually sent                              |
| `04_optimistic.tsx`         | Cancel, snapshot, guess, roll back. Why `cancelQueries` is the step you cannot skip                                           |
| `05_infinite.tsx`           | `useInfiniteQuery`, cursors over offsets, and letting the server decide where the list ends                                   |

### The mock network

| File                          | What it is                                                                                           |
| ----------------------------- | ---------------------------------------------------------------------------------------------------- |
| `src/api/handlers.ts`         | The request handlers. Written once, used in both environments                                        |
| `src/api/browser.ts`          | `setupWorker`, a Service Worker, for `npm run dev`                                                   |
| `src/api/server.ts`           | `setupServer`, an HTTP interceptor, for Vitest                                                       |
| `src/api/db.ts`               | In-memory data, reset between tests                                                                  |
| `src/api/client.ts`           | The `fetch` layer: throws on a non-2xx, carries the status, threads the abort signal                 |
| `public/mockServiceWorker.js` | Generated by `npx msw init public`. Committed, and has to be, or the browser has nothing to register |

## Run it

```bash
npm install                          # from the repo root, once
npm run dev -w learning/data-fetching
npm test -- --project data-fetching
```

Open the React Query devtools in the corner. Every cache entry, its key, whether
it is stale, and who is subscribed to it, which turns "why did that refetch"
into something you read rather than guess.

## Why MSW rather than mocking fetch

Stubbing `global.fetch` or mocking the module that calls it tests a version of
your code with a seam cut into it. MSW intercepts at the network layer, so the
component makes a real request through the real client, and the only thing
swapped out is the server. The same handlers then run the browser demo, which
means the mock and the thing you clicked through cannot drift apart.

`onUnhandledRequest` differs between the two on purpose. Tests use `"error"`, so
a typo in a URL fails with "no handler for GET /api/bookmark" instead of hanging.
The browser uses `"bypass"`, because the worker also sees Vite's own asset
requests.

## Three things that bit while writing the tests

**Counting requests is the only honest cache test.** Both panels in lesson 01
end up showing the right rows. `server.events.on("request:start", …)` is what
shows one of them asked three times and the other twice.

**A cache hit does not mean no request.** With the default `staleTime: 0`, a
revisit renders from cache _and_ refetches behind it. That is usually what you
want and it made the first version of lesson 01's assertion wrong.

**An in-flight request outlives the test that started it.** A vote asserted
optimistically, with the test ending before the 300ms request landed, wrote to
the fake database _after_ `afterEach` had reset it, and the next test started one
vote ahead. Wait for the write to land, not just for the screen to update.

## Not covered here

cache to storage, and the server-side story where the data is fetched before the
JavaScript ships. The last of those belongs in next-app-router.
